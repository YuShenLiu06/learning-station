# 轻量需求到验收循环

## 使用前

此 Skill 保存于当前对话的附件与工作区，供后续任务显式读取；没有因此安装到用户电脑或注册为云端自动发现能力。它规定做事流程，不扩大工具、费用或合并权限。

1. 先复述目标、非目标、可观察验收条件和风险，请用户确认后再派发实现。列出任务与建议模型，尊重当次预算及暂停指令。
2. 一个可独立测试、回滚的功能一个分支/worktree/PR；按相对目标分支最终 diff 的 additions + deletions 合计不超过 1000 行（含测试和文档）。生成文件计入总数并单独披露，不隐藏规模；无法合理拆分时报告例外，不能硬拆半个功能。
3. 小 PR 面向本批次集成分支；并行任务不能共同写一个工作目录。依赖任务先约定接口及顺序。提交前运行确定性检查，记录 HEAD SHA、测试与未测项。
4. 触发仓库已配置的 Codex Code Review 与 Security Review，确认两者确实执行且覆盖目标 SHA。入口或权限不可用时报告阻塞；没有评论不等于审查已完成，也不等于没有所有级别的缺陷。
5. 将有效发现交回实现者；附位置、复现、影响和验收标准。误报需证据，不为了让审查闭嘴而无意义修改。修复后更新 SHA、补回归测试并复查；合并重复发现，避免重复修复。
6. 通过的小 PR 在集成分支组合，保留每功能可识别的提交；验证组合场景、共享状态及冲突处理，最终对主分支开验收 PR。按 feat/bugfix/chore、风险与批次标签分类，提供小 PR 索引、候选 SHA、可运行产物、测试步骤及剩余风险。
7. 用户本人测试并明确确认对应版本后才可合主。候选代码又变更则重新确认受影响部分；不把自动测试或机器人批准当用户验收。
8. 每批结束由 GPT-6-Luna 总结有效返工，按 [返工总结](references/feedback.md) 提出小范围规则更新候选。记录成功与失败，不自动改审查门槛或发布规则。

## 调度和预算

确定性操作用脚本。建议默认：GLM-5.3-Flash 做明确局部实现；GLM-5.3 做边界清楚的复杂工程；Luna 整理证据和返工；GPT-6.1-Sol 做复杂诊断、关键设计及高风险前置判断。Astra 不自动升级，先取得用户确认。原生审查服务的模型由实际产品设置决定。

每轮先排除环境故障和缺上下文。默认同一问题两轮有效修复仍无进展就整理证据、调整方法或请求升级；不是两轮后带问题通过。缺额度/权限、需求超范围或用户暂停时停止相关操作。默认 Standard，预算不明时不启动无限循环或额外付费调用。

## 审查规则怎么加载

- Codex GitHub 官方支持 AGENTS.md；关键规则直接放其中，详细规则可放 REVIEW.md，并在 AGENTS.md 明确要求读取。不要假定文件名会自动注入。
- 代码质量审查同时显式读取同项目的 `skills/yushen-code-quality-review/SKILL.md`（按实际安装路径调整）；外部替代实现只出 PR 建议，未经用户采纳不改代码。若该技能未安装，报告缺口，不假装执行。
- 创建规则时参考 [REVIEW.md 实例](references/REVIEW.example.md)。实例是学习站示例，其他仓库必须适配，不能复制不存在的业务约束。
- REVIEW.md 放长期、项目特有、可判断的审查标准；每次 PR 的发现与证据留在 PR。CI 负责格式、类型和其他确定性规则。
- 官方依据：https://learn.chatgpt.com/docs/third-party/github （2026-10-17 核验）。行为变化时复查官方文档。

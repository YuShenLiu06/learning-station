## 目标与范围

把“可调用哪些工具”“可访问哪些资源”和“谁批准 Bash”分开表达。方向是将 `read` 与 `write` 合并为一个读写能力，同时保留 Bash 的三种逐次决策方式：本人逐次批准、AI 审批、本人选择全部放行。

三种方式只决定是否需要为当前 Bash 调用取得批准。它们不能扩大工具白名单、课程资料授权、文件路径范围、网络范围、进程权限或凭据可见范围。以下设计只定义概念和验收标准，不改变运行时行为。

## 当前实现与缺口

基于 `src/toolAuthorization.ts`、`src/ComposerToolTierPicker.tsx`、`src/ToolAuthorizationSettings.tsx`、`src-tauri/src/authorized_tools.rs`、`src-tauri/src/model.rs`、`pi-sidecar/learning-plugin.mjs` 和 `contracts/pi-native-session-v1.md`：

- 当前档位为 `off/read/write/bash`，逐级累积开放工具，默认 `off`。Rust 从本机偏好读取档位并构造工具白名单；读取失败时收紧为 `off`。读、写、命令工具只在 `question` / `explain` 模式按设置注册，Rust 执行时还会核对会话、运行和工具档位。
- `read` 可读本轮冻结 manifest 中获准的来源，或当前会话工作区中的文件；读取来源时会核对运行快照与版本。`write` 只写当前会话的 `files` 工作区，并校验相对路径、符号链接、文件数和总容量。这里的“读写一体”只能合并开关，不能把读取和写入变成同一资源范围。
- `bash` 由 Rust 启动 `/bin/bash -c`，将工作目录设为该会话的 `files`，清空继承环境后只设置 `PATH` 和 `LANG`，关闭标准输入，并限制命令长度、运行时长和输出。当前代码没有每次执行前的本人或 AI 审批界面，也没有独立的 Bash 资源策略。
- `current_dir(files_root)` 只设置进程启动时的工作目录；`env_clear()` 只清理继承环境。二者都不限制命令随后访问其他文件、网络或子进程，不构成 OS 沙盒。Bash 以应用相同的 OS 用户身份运行，可触达该身份本来可访问的资源。不能把“仅在会话工作区执行”当成现有硬隔离保证。
- `ui-preferences` 保存的是应用级工具档位；输入区左下角可在生成前选择，生成进行中 UI 禁止切档，Rust 对 queued/running 也返回 `BUSY`。这不是逐次授权，也不能撤销已经运行的命令。
- 当前写入和 Bash 结果按稳定操作号写入会话目录下的回执，恢复按原操作号读取而不重新执行；缺失回执时可报告结果未知。设置页只列最近最多 200 条写入/命令摘要，不显示命令原文、参数或文件内容。
- 回执文件位于 `workspaces/<sessionId>/receipts`，Bash 工作目录位于同一会话目录的 `files`。二者同属本机用户可写状态；同 UID 的进程可触达并可能篡改或删除回执。当前回执不能作为抵御同 UID 篡改的独立证明。这个结论由路径与进程身份推得，本次没有执行篡改检查。

### Pi 现成能力的核验范围

Pi 官方[安全文档](https://pi.dev/docs/latest/security)说明：Pi 工具及扩展使用启动 Pi 的账户权限；项目工作目录不会限制命令可访问的路径；Pi 不会逐次询问每个工具调用。官方仓库[权限与容器化说明](https://github.com/earendil-works/pi#permissions--containerization)提到 Gondolin、Docker、OpenShell 等隔离运行模式。

以上是 2026-10-20 检索到的 Pi 官方当前文档。仓库锁定的是 `@earendil-works/pi-coding-agent` 1.3.0；本文没有从该锁定包验证这些模式的 API、与当前 Rust 侧 Bash 执行路径的适配或 macOS 实际隔离强度。因此这里只作为待研究的上游背景，不把它们描述成学习站现成能力或已验证的可直接采用方案。当前 Bash 由 Rust 子进程启动，不能假设 Pi 的内建工具或 Node 权限标志会限制它。

## 方案草案

### 三个独立维度

| 维度 | 草案 | 负责回答的问题 |
| --- | --- | --- |
| 工具能力 | 关闭；或开启受控读写；Bash 是否开放另行选择 | 模型可请求哪些工具？ |
| 资源范围 | 本轮明确获准的资料、当前会话工作区，以及未来经用户选择且由执行边界实际实施的资源 | 工具能触达哪些文件、进程、网络和凭据？ |
| Bash 决策方式 | 本人逐次批准；AI 审批；全部请求放行 | 对一个已获准、范围内的 Bash 请求，是否需要等待批准？ |

未来准入应由统一的学习工具策略、用户对具体工具和 Bash 决策方式的明确选择，以及相应资源范围与实际执行边界共同决定；`question` / `explain` / `review` 等任务模式不再作为工具是否可用的条件。若未沙盒 Bash 被允许，其范围必须如实表达为当前账户可访问的资源，不能把文案当成隔离。批准方式不跳过其他条件。`全部请求放行`在本文中解释为用户当前选择的范围内所有合格 Bash 请求免逐次确认；不代表允许任意本机资源，也不自动开放读写工具。若 Issue 原意是把三种方式同时用于读写调用，应先由 Sol 澄清。上文按基线代码记录当前模式限制，属于现状描述，不是目标行为。

### 旧配置的无提权迁移

迁移保留旧配置已经明确授予的能力，不因旧 `read` 值直接打开新合并读写开关。`read` 的一次性兼容状态只维持原有读取能力，不是新产品的长期档位；用户明确选择新读写开关后才增加写入能力。旧 `bash` 也不代表已选择未来的审批方式：迁移后先暂停 Bash，用户明确选定批准方式前不启动命令。

| 旧配置 | 迁移结果 | 用户动作与限制 |
| --- | --- | --- |
| `off` | 工具关闭、Bash 关闭 | 不增加任何能力。 |
| `read` | 进入一次性只读兼容状态，沿用原读取范围；写入与 Bash 关闭 | 提示用户选择关闭，或明确开启统一读写。不能把只读兼容状态保留成永久产品档位；用户选择前不得写入。 |
| `write` | 开启统一读写，保留旧读写实际范围；Bash 关闭 | 因旧 `write` 已包含读写能力，不扩大到其他路径、资料、网络或凭据。 |
| `bash` | 保留旧配置已包含的读写范围；Bash 暂停并标为待用户选择 | 用户明确选择人工逐次批准、AI 审批或全部请求放行后才可能启用 Bash。不得从旧值推断 AI 审批或全部放行，也不得在待选择期间启动命令。 |
| 缺失、无效或未知值 | 工具关闭、Bash 关闭 | 失败关闭；不得猜测、回退到更宽档位或自动修复成允许状态。 |

迁移提示应解释哪些旧能力被保留、哪些功能暂时关闭，以及继续使用所需的明确操作。迁移只改变偏好表达，不改变会话资料、资源范围或 OS 执行边界。

草案默认保持工具关闭。开启统一读写时，`read` 与 `write` 一起注册，但各自保留不同的数据边界。若另行开启 Bash，建议逐次人工审批为默认方式；AI 审批与全部放行均需本人明确选择。AI 审批服务的身份、上下文和降级行为，以及全部放行的提示与持久范围尚未定案。

资源范围的文字披露不构成强制隔离。`cwd`、`env_clear` 和界面说明都不能阻止 Bash 访问当前账户本来可访问的资源。是否允许未受 OS 沙盒保护的 Bash 执行仍是待 Sol 决策的产品边界：若允许，必须准确披露其真实访问能力且不得声称“仅限工作区”；若产品承诺强制限制，则没有有效 OS 执行边界的配置必须拒绝启动。本文不主张所有环境都已具备或必须始终具备同一种隔离机制。

界面可参考 ChatGPT 的三选项形式呈现 Bash 决策方式，但每项应直接说明批准者、请求是否逐次确认和当前资源边界；不得只用“安全/自动”等模糊名称。样式参考不改变本文的默认关闭和范围约束。

### 请求和批准的绑定

- 展示审批前冻结调用内容：稳定请求号、命令、工作目录、工具档位、资源范围摘要和策略版本。人工批准只对这一个未过期请求有效；内容、工作目录、范围或策略任何一项改变都必须重新审批。
- 人工拒绝不得启动命令。审批超时或窗口关闭只有在 Rust 后台可证实请求仍待批/未批准且命令尚未派发时，才能给出零启动结论。若批准已被接受，或命令已派发后确认回执/IPC ack 丢失，则保留 `unknown`，以原请求号只读核对；不能把它说成拒绝或零启动，也不能换新请求重执行。拒绝/过期不能被当成批准缓存。批准与执行结果分别记录，避免把“批准了”显示成“执行成功”。
- AI 审批必须由独立于执行代理的 reviewer 路径作出，不能让执行代理自行批准自己的命令；reviewer 返回明确、可校验的允许或拒绝结果。调用失败、超时、格式无效或后台尚未接受有效允许结果时失败关闭，不切换到人工已批准或全部放行。若允许结果已被接受但确认丢失，按 `unknown` 处理，不推断命令未启动，也不自动切换审批路径。AI 审批不是资源隔离，也不能作为独立于模型注入风险的安全边界。
- 全部放行仍逐条检查工具和资源边界、命令参数预算、执行时限、结果状态与撤销状态。模式打开时界面持续标识当前选择和实际范围，不以一次启用静默扩大权限。
- 拒绝、超时和运行中撤销均不声称回滚已发生的副作用。执行完成但返回丢失时先以原请求号核对；未知或不可信回执不得自动重放。

## 验收矩阵

所有验收均使用合成数据和无提权环境，不使用用户真实资料、权限、凭据或付费模型。只有声称验证 OS 隔离的用例才必须运行在对应隔离边界实际生效的环境；未隔离配置的验收只能验证风险披露、启动策略和未作虚假承诺，不能据此声称资源被限制。`未执行`的命令必须有可观察的零启动证据；UI 流程以实际原生窗口验证，fixture/mock 只支持其对应测试层结论。

| 场景 | 输入/触发 | 必须观察到的结果 | 恢复与禁止行为 |
| --- | --- | --- | --- |
| 默认关闭 | 新安装、偏好缺字段或偏好读取失败，模型请求 read/write/bash | 工具未注册或被 Rust 拒绝；不创建命令进程；状态保持关闭 | 提示如何由本人开启；不因模型要求自动开启 |
| 有效旧配置迁移 | 分别提供旧 `off`、`read`、`write`、`bash` 配置 | `off` 全关；`read` 仅保留原读取范围且不写入；`write` 映射为保持原范围的统一读写且 Bash 关闭；`bash` 保留原读写范围但 Bash 暂停待选择 | `read` 用户明确选择统一读写前不获得写入；旧 `bash` 用户明确选择审批方式前零启动；不得把旧 Bash 映射为 AI 审批或全部放行；迁移不扩大任何资源范围 |
| 未知旧配置 | 配置值未知、损坏或结构不兼容 | 失败关闭，工具和 Bash 均不可用；有可理解的恢复提示 | 不猜测、不自动映射为允许；用户显式重新选择后才启用 |
| 读写一体 | 本人开启受控读写，不开放 Bash | 本轮获准来源和会话工作区读取、会话工作区写入可用；其他课程/任意本机路径仍拒绝；Bash 不注册 | 拒绝提供明确原因；不得把读写开关解释为“任意文件读写” |
| 人工逐次拒绝 | 发出一个有效 Bash 请求，本人点拒绝；后台确认拒绝且未派发 | 该冻结请求不启动；结果为拒绝，相关活动/回执不伪装成完成 | 可由本人重新发起新请求；同一拒绝不能在重试中改成允许；若确认丢失，按 `unknown` 核对 |
| 人工逐次批准 | 本人查看命令、工作目录、范围和影响后批准 | 只执行展示过且摘要匹配的单次请求；同一请求重复交付不重复执行 | 参数或策略变化须重审；再次执行须新请求和新批准 |
| 人工审批待决超时/关闭 | 用户不操作或关闭审批窗口；Rust 后台仍能确认请求待批/未批准且未派发 | 标记为过期/拒绝，观察到零启动证据；不得将过期作为批准缓存 | 用户可查看原请求后自行重试；不能默认为批准或自动转 AI/全部放行 |
| 批准/派发确认丢失 | 批准可能已被接受，或命令派发/返回 ack 丢失，导致 UI/IPC 结果不明 | 保留审批或执行结果 `unknown`；使用原请求号只读核对后台状态与既有回执 | 后台未能证明未派发时不得宣称零启动；不换请求号、不自动重放，必要时提示用户检查副作用 |
| AI 拒绝 | AI 审批返回拒绝且后台确认未派发 | 命令未启动，拒绝原因用安全、可理解的摘要展示 | 人工可另行发起新决定；不得覆盖/伪造 AI 判定；若确认丢失，按 `unknown` 核对 |
| AI 审批不可用 | AI 超时、连接失败、输出不合法，或 reviewer 未配置，且后台确认未接受允许决定 | 失败关闭，命令未启动，状态区分超时/拒绝 | 只可重试审批或改由本人显式选择人工模式；不自动放行。若允许决定已被接受但确认丢失，按“批准/派发确认丢失”处理 |
| AI 审批隔离 | 执行模型生成命令或混入不可信材料中的命令 | reviewer 只收到经确认的最小请求材料；攻击性材料不能改变固定审批规则或资源范围 | reviewer 不能替用户扩大范围；AI 误判风险需单列，不能标为 OS 隔离通过 |
| 全部放行 | 本人明确切换到全部放行后，请求范围内 Bash | 范围合格请求不出现逐次确认；超范围请求仍拒绝；界面持续显示放行模式 | 关闭/切回后新的请求立即按新策略；不撤销已发生副作用；必须测试本人能找回切换入口 |
| 超出资源范围 | 命令尝试访问会话目录外文件、网络或不允许的进程 | 若产品承诺限制，OS 执行边界须实际阻断并留下可核验结果；仅设置 cwd/env 不算通过 | 若未实现强制边界，界面如实说明 Bash 可能使用当前账户可访问的资源，禁止宣称“仅工作区” |
| 撤销等待中的批准 | Bash 请求正在等待本人/AI 审批时关闭 Bash 或撤销授权 | 待决 token 作废，命令不启动，迟到批准被拒绝 | 用户需重新发起请求；不得复活过期批准 |
| 撤销运行中的命令 | Bash 已启动时关闭 Bash/撤销当前授权 | 系统尝试终止相应进程组；只有确认退出后才显示已停止，否则为结果未知；不说已撤销副作用 | 不自动重跑；提示检查工作区或受影响资源 |
| 命令执行超时 | 在合成工作区运行可控的长命令 | 到时终止可控进程组并记录 timed-out；输出保留上限，实际副作用标为可能已发生 | 按原请求号核对；不自动重试，不以超时等同无执行 |
| 响应丢失/结果未知 | 命令完成后丢失 IPC/应用关闭，或没有可信终态 | 活动显示未知；以原请求号和参数摘要只读核对；证据完整时展示既有结果，不再执行 | 无证据/冲突/损坏时保持未知并提示人工检查；不得换新 ID 静默重放 |
| 重复投递与参数冲突 | 同一请求号重复相同参数，或同 ID 携带不同参数 | 相同请求最多执行一次并返回可核验原结果；异参返回冲突且不执行 | 需要新动作时由用户明确发起新请求，不能自动换号绕过冲突 |
| 回执被同 UID 篡改 | 合成环境中删除、替换、篡改或制造回执文件 | 要么通过不受 Bash 同 UID 写入的完整性机制检测并标记无效，要么回执只作提示，不作为执行成功/授权证明 | 不读取无效回执来重放命令；保持 unknown 并要求核验。若无法满足任一条件，不得把本地 JSON 回执称为可信审计证据 |
| 关闭/重开后恢复 | 关闭应用后重开，读取审批历史与执行回执 | 可区分未批准、拒绝、过期、执行完成、超时、未知和无效回执；敏感命令内容按明确保留策略处理 | 未知不自动执行；保留必要的请求标识和用户输入，提供可操作的检查下一步 |

### 交付验收证据

- Rust 单测验证策略矩阵、审批绑定、超时、撤销、幂等/冲突与回执完整性；Node/Pi 桥接测试验证工具注册/拒绝/状态回传；原生 GUI 记录本人批准、拒绝、超时、撤销和恢复的实际步骤及截图。
- 所有命令验证限于人工编写的合成、非提权检查。隔离边界测试必须证明访问被实际 OS 机制阻止；mock 结果不能证明沙盒或 GUI 成立。
- AI 审批单测使用确定性的合成 reviewer；真实模型、真实凭据、计费和用户文件不纳入默认自动验收。若将来要做真实服务验收，须另有明确授权。
- 测试绑定最终源码 SHA。分别报告单测/桥接、实际 GUI、真实模型服务和未测平台；一层通过不能替代另一层。

## 需要 Sol 复核的高风险事项

1. **资源边界与产品承诺：** 是否允许未受 OS 沙盒保护的 Bash 执行？若允许，哪些审批模式可出现，如何准确披露账户可访问的文件、网络、子进程与凭据范围？若要求强制“仅工作区”，需选定并验证何种 OS 执行边界；文字提示不能替代边界。本文保留该产品决策，不宣称所有场景已有强制隔离。
2. **AI 审批信任模型：** 如何实现 reviewer 路径独立于执行代理，并处理提示注入、缺失上下文、模型错误、计费、请求/命令内容保留和 reviewer 本身的权限？具体 AI 服务与权限仍待确定；失败是否 fail-closed 已按草案要求。
3. **全部放行的作用范围：** 是每次会话、单个会话的持久偏好还是应用级偏好？是否要求二次确认、可见常驻提示、重新打开应用后重置？本文仅把它解释为范围内 Bash 调用免逐次审批。
4. **撤销与进程语义：** 关闭授权是否只影响后续调用，还是立即终止在途命令？多进程、后台守护进程、kill 失败及已提交副作用怎样呈现？
5. **回执威胁模型：** 同 UID 可写状态目录时，是否采用受保护完整性密钥/不可变审计机制，还是明确回执仅用于用户查看且不作为安全证明？需要明确权限保存、命令敏感信息和保留期。
6. **Pi 隔离候选适配：** 官方文档所列隔离模式是否适用于学习站锁定的 1.3.0 依赖、Rust 启动的 Bash 路径及目标平台？当前未验证，不应先据此选库或改架构。
